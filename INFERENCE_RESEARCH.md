## 1. Can Auto Track submit two jobs sequentially?

**Yes at the HTTP job API level; the current high-level SDK wrapper is not a pure submit operation.**

The active YOLO entrypoint creates `YOLOv8Model`, which inherits `ObjectDetection` → `Inference`. It does not override the video endpoints. `/inference_video_id_async` validates state, schedules `_inference_video_id`, and returns `inference_request_uuid` without waiting for inference. Results/progress and Stop are separate requests. Conversely, `/inference_video_id` waits on `future.result()`. [YOLO entrypoint](https://github.com/supervisely-ecosystem/yolov8/blob/b5503275bb4620dfa8b3f308c374bde644cce403/serve/src/main.py#L16), [inheritance](https://github.com/supervisely-ecosystem/yolov8/blob/b5503275bb4620dfa8b3f308c374bde644cce403/serve/src/yolov8.py#L49), [SDK endpoints](https://github.com/supervisely/supervisely/blob/ed04d3af8bb34fdc474d4178945bb30be5741250/supervisely/nn/inference/inference.py#L3707).

Important constraints:

- `Session.inference_video_id_async()` submits, stores a single mutable UUID, then polls `_wait_for_async_inference_start()` before returning an iterator. Polling sleeps one second, has no default deadline, and infers startup from result/progress fields rather than an explicit running status. Calling it again on the same `Session` stops the preceding job. Two raw submissions with separately owned UUIDs avoid that coupling; two independent Sessions still retain startup waiting. [Wrapper](https://github.com/supervisely/supervisely/blob/ed04d3af8bb34fdc474d4178945bb30be5741250/supervisely/nn/inference/session.py#L291), [waiting](https://github.com/supervisely/supervisely/blob/ed04d3af8bb34fdc474d4178945bb30be5741250/supervisely/nn/inference/session.py#L540).
- In the inspected SDK, `multithread_inference=True` is the default. YOLO's entrypoint leaves it unchanged. The executor uses `max_workers=None` (Python's default pool size); setting the option false produces one worker. Thus this implementation does **not** enforce a single-job queue by default. Each request receives its own result/progress/stop state. [Executor](https://github.com/supervisely/supervisely/blob/ed04d3af8bb34fdc474d4178945bb30be5741250/supervisely/nn/inference/inference.py#L167), [scheduler](https://github.com/supervisely/supervisely/blob/ed04d3af8bb34fdc474d4178945bb30be5741250/supervisely/nn/inference/inference_request.py#L461).
- Executor concurrency does not guarantee concurrent model execution or a speedup. YOLO shares one `self.model`; its active batch path calls `predict_benchmark()`. Current upstream Ultralytics reuses a predictor and guards its inference loop with `_lock`. This lock was verified in upstream `main`, **not** in the running container or the Dockerfile-pinned `8.3.15` predictor source. Shared model settings/state and actual throughput require verification on the deployed version. [YOLO batch prediction](https://github.com/supervisely-ecosystem/yolov8/blob/b5503275bb4620dfa8b3f308c374bde644cce403/serve/src/yolov8.py#L542), [Ultralytics predictor](https://github.com/ultralytics/ultralytics/blob/main/ultralytics/engine/predictor.py), [8.3.15 predictor reuse](https://github.com/ultralytics/ultralytics/blob/v8.3.15/ultralytics/engine/model.py).

**Recommendation:** submit forward and backward jobs consecutively, retain both UUIDs, and poll/cancel each independently. Subprocesses are unnecessary for this submission pattern. There is no evidence for promising identical speed: the second submission has a network delay, and serving scheduling, batching and model serialization determine throughput. Stop is cooperative: the endpoint sets an event and video inference checks it between batches; it does not interrupt an executing model call. [Cancellation](https://github.com/supervisely/supervisely/blob/ed04d3af8bb34fdc474d4178945bb30be5741250/supervisely/nn/inference/inference.py#L3938), [batch loop](https://github.com/supervisely/supervisely/blob/ed04d3af8bb34fdc474d4178945bb30be5741250/supervisely/nn/inference/inference.py#L2400).

## 2. Is backward already supported?

**The inspected SDK already supports reverse frame traversal in both detector and geometry-tracking paths, but one client parameter is inconsistent.**

| Path | Verified behavior |
|---|---|
| YOLO `/inference_video_id[_async]` | Reads `state.direction`, builds descending frame indices for `backward`, downloads those frames, and runs ordinary per-frame detection in batches. This is not propagation of manually seeded objects. |
| SDK `Session(..., frames_direction="backward")` | Serializes `framesDirection`, while the active server reads only `direction`: the wrapper's backward parameter is ignored in the inspected version. |
| `BBoxTracking`, `MaskTracking`, `PointTracking`: `/track-api` | All pass `context.direction` to `TrackerInterface`, whose frame traversal already decrements for backward. This endpoint returns geometry predictions after completing the request. |
| Newer tracker `/track_async` paths | `TrackerInterfaceV2` also builds descending indices. These paths use figures and their own result/progress lifecycle; they are not a drop-in replacement for Auto Track's `/track-api` calls. |
| `/track-api-files` | Each handler consumes uploaded files in the supplied order. Bbox/point handlers use ascending nominal indices only to limit iteration; mask also reads direction. Supplying seed-frame-first reversed files is mechanically supported by these base handlers; a specific model override still needs checking. |

Sources: [detector range and frame labels](https://github.com/supervisely/supervisely/blob/ed04d3af8bb34fdc474d4178945bb30be5741250/supervisely/nn/inference/inference.py#L2337), [client serialization](https://github.com/supervisely/supervisely/blob/ed04d3af8bb34fdc474d4178945bb30be5741250/supervisely/nn/inference/session.py#L639), [TrackerInterface traversal](https://github.com/supervisely/supervisely/blob/ed04d3af8bb34fdc474d4178945bb30be5741250/supervisely/nn/inference/tracking/tracker_interface.py#L292), [V2](https://github.com/supervisely/supervisely/blob/ed04d3af8bb34fdc474d4178945bb30be5741250/supervisely/nn/inference/tracking/tracker_interface.py#L440), [bbox API](https://github.com/supervisely/supervisely/blob/ed04d3af8bb34fdc474d4178945bb30be5741250/supervisely/nn/inference/tracking/bbox_tracking.py#L186), [mask API](https://github.com/supervisely/supervisely/blob/ed04d3af8bb34fdc474d4178945bb30be5741250/supervisely/nn/inference/tracking/mask_tracking.py#L397), [point API](https://github.com/supervisely/supervisely/blob/ed04d3af8bb34fdc474d4178945bb30be5741250/supervisely/nn/inference/tracking/point_tracking.py#L298), [bbox files](https://github.com/supervisely/supervisely/blob/ed04d3af8bb34fdc474d4178945bb30be5741250/supervisely/nn/inference/tracking/bbox_tracking.py#L540), [mask files](https://github.com/supervisely/supervisely/blob/ed04d3af8bb34fdc474d4178945bb30be5741250/supervisely/nn/inference/tracking/mask_tracking.py#L525), [point files](https://github.com/supervisely/supervisely/blob/ed04d3af8bb34fdc474d4178945bb30be5741250/supervisely/nn/inference/tracking/point_tracking.py#L382).

A deterministic, dependency-free extraction of the client state builder reproduced the mismatch: start 100, count 3, `frames_direction="backward"` produces server indices **100,101,102**; adding `state.direction="backward"` produces **100,99,98**. No live inference was involved.

The old `InferenceVideoInterface` file remains in the SDK and even clears its reverse index list, but the active inherited YOLO video endpoint does not use that class. Likewise, YOLO's `predict_video()` override is not the active `videoId` batch path. Do not infer current endpoint behavior from those leftover implementations. [Legacy helper](https://github.com/supervisely/supervisely/blob/ed04d3af8bb34fdc474d4178945bb30be5741250/supervisely/nn/inference/video_inference.py#L69), [active batch dispatch](https://github.com/supervisely/supervisely/blob/ed04d3af8bb34fdc474d4178945bb30be5741250/supervisely/nn/inference/inference.py#L1928).

Auto Track currently calls synchronous `/track-api` without direction and uses synchronous `Session.inference_video_id()` for its detector. Backward therefore requires changes to Auto Track's planning, result-to-frame mapping, and progress; it does **not** inherently require adding backward to every serving. Check each selected serving/version for overrides and shared tracker state before running two jobs concurrently. In particular, base bbox tracking calls `self.initialize()` on the shared model, so separate request UUIDs alone do not establish model-state isolation. [Auto Track calls](src/tracking/inference.py), [shared bbox initialization](https://github.com/supervisely/supervisely/blob/ed04d3af8bb34fdc474d4178945bb30be5741250/supervisely/nn/inference/tracking/bbox_tracking.py#L245).
